## 1. Background

This is the first project in the capstone series and the only one built on synthetic data.

Its purpose was to establish capability before establishing focus: build a full-breadth
university analytics dashboard end to end — filters, KPI cards, multi-tab layout,
drill-down, export, branding — without the constraint of what public data actually supports.

The three dashboards that follow invert this deliberately. Each answers **one** question on
**real** IPEDS data, with a hard no-synthetic-data rule. This project is the control case
that made that contrast a considered choice rather than a limitation.

---

## 2. The Question

> **What does a full-breadth university analytics dashboard look like, end to end?**

Deliberately a design and engineering question, not an analytical one. There is no finding
here, because the data is invented.

---

## 3. The Central Constraint

**All data is synthetic.** It is generated by `generate_data.py` and describes no real
institution.

The dashboard is YU-*branded* — navy `#0033A0` with a gold accent — which makes the
synthetic-data disclaimer load-bearing rather than decorative. A branded dashboard showing
plausible-looking enrollment and revenue figures is exactly the artifact most likely to be
screenshotted out of context and mistaken for real institutional reporting.

Mitigations, all of which must stay in place:

- The README opens with a "Scope — read this first" section stating the data is synthetic.
- The app carries a visible synthetic-data note.
- No figure from this project is ever cited as a fact about YU.

## 5. Data

Three synthetic tables, generated deterministically (`SEED = 42`) so output is identical
across runs:

| File | Grain | Contents |
|---|---|---|
| `data/metrics.csv` | One row per (year, department) | Enrollment, admissions funnel, faculty, revenue |
| `data/students.csv` | Student-level sample | ~3% of total enrollment per department-year |
| `data/courses.csv` | Course-section level | Year, term, course, capacity, fill rate, grades |

**Range:** 2015–2025. **Departments:** Engineering, Business, Arts & Sciences, Education,
Nursing, Law — each with 2–4 majors.

### Internal consistency

The generator models a gentle upward enrollment trend with a COVID-era dip, then derives
faculty count, student-faculty ratio, and tuition revenue *from* enrollment. This matters:
generating each metric independently would produce combinations that cannot occur in
reality — a student-faculty ratio that contradicts the headcount, revenue unrelated to
enrollment — and the dashboard would look plausible while being internally incoherent.

Fake data still has to be *consistent* fake data to be a useful UI exercise.

### Determinism

The fixed seed is a requirement, not an incidental choice. Unseeded randomness would shift
the numbers on every run, silently invalidating every screenshot and written description of
the dashboard.

## 6. Delivered Scope

Six tabs over one shared sidebar filter state:

| Tab | Contents |
|---|---|
| **Enrollment** | Headcount trends by year, department, residency, gender |
| **Academics** | Academic performance metrics and distributions |
| **Courses** | Sections by term and level, fill rates, enrollment-vs-grade scatter, searchable catalog |
| **Admissions** | Applications → admits → enrolled funnel, snapshot by year |
| **Finance & Ops** | Tuition revenue, faculty counts, student-faculty ratio |
| **Data** | Department drill-down (major, enrollment status, top sections) and CSV export |

Plus:

- **Sidebar filters** — year range, department multiselect, residency, gender, term —
  applied across all tabs
- **KPI cards** — headline metrics with year-over-year deltas
- **Export** — filtered metrics, students, and course catalog as CSV

**Design rule:** a filter set in the sidebar must affect every tab that can honor it. A tab
silently ignoring the active filter is the fastest way to make a dashboard lie, and it is the
single most common defect in multi-tab dashboards.

---

## 7. Explicit Non-Goals

This dashboard does **not**:

- Describe Yeshiva University or any real institution
- Support any real decision
- Use a database or backend — flat CSVs are deliberate
- Include authentication or access control
- Optimize for mobile

---

## 8. What This Project Established

Carried forward into the three IPEDS dashboards:

- **Streamlit and Python dashboard mechanics** — reused directly in the tuition dashboard.
- **Shared filter state across views** — the pattern behind the institution toggles and year
  range controls in every later project.
- **YU brand palette** — `#0033A0` here, `#00205B` in the tuition dashboard.
- **The value of narrowing.** Six tabs of synthetic breadth made the case for one sharp
  question on real data. The later PRDs' "one measure, one claim" principle is a direct
  reaction to this project.

Deliberately **not** carried forward: synthetic data, in any form, anywhere.

---

## 9. Deployment

**Not publicly hosted. Runs locally.**

This dashboard **cannot be hosted on GitHub Pages** — Pages serves static files only, and
this is a Streamlit app requiring a running Python process.

Unlike the tuition dashboard, it has **no database dependency**: the data is flat CSVs
generated at first run. Publishing to **Streamlit Community Cloud** (free) is therefore
straightforward — point it at this repo and `app.py`, with no secrets or external services
required. Not currently set up, but nothing blocks it.

---

## 10. Success Criteria

1. The dashboard runs end to end with no broken tabs or errors.
2. Sidebar filters affect every tab that can honor them.
3. No viewer mistakes the synthetic figures for real institutional data.
4. Regenerating the data produces byte-identical output.
